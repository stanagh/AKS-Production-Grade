# AKS Production-Grade Platform

This is a production-style deployment of a containerised .NET application (AttendanceCRM) on Azure Kubernetes Service, using Terraform, Azure DevOps CI/CD pipelines, GitOps with ArgoCD, and a full platform layer for ingress, TLS, DNS, secrets and monitoring.

The application is publicly accessible via HTTPS with certificates issued automatically by Let's Encrypt.

## At a glance

| Area | What's used |
| --- | --- |
| Infrastructure as Code | Terraform (reusable modules), remote state in Azure Storage |
| Compute | AKS, autoscaling node pool and Horizontal Pod Autoscaler  |
| CI | Azure DevOps multi-stage YAML pipelines with an approval gate |
| CD | GitOps with ArgoCD (automated sync, prune, self-heal) |
| Ingress and TLS | NGINX ingress, cert-manager with Let's Encrypt (DNS-01) |
| DNS | external-dns managing records in Azure DNS |
| Identity | Entra Workload Identity, one managed identity per workload |
| Secrets | Azure Key Vault through the Secrets Store CSI driver |
| Data | Azure SQL Database |
| Observability | Prometheus, Grafana, Alertmanager, Container Insights, Application Insights, Azure Monitor alerts |
| Security scanning | Checkov (Terraform code), Trivy (container image) |

## How a change reaches production

**An infrastructure change** (anything under `terraform/`):

1. A push to `main` triggers `azure-terraform-push.yml`.
2. Terraform runs `init`, `validate` and `plan`, and saves the plan as a pipeline artifact.
3. Checkov scans the Terraform code.
4. The pipeline pauses for manual approval on the `production` environment.
5. The saved plan is applied, so what was reviewed is exactly what runs.
6. Slack is notified.

**An application change** (anything under `AttendanceCRM/`):

1. A push to `main` triggers `azure-app-ci-cd.yml`.
2. Unit tests run.
3. The image is built and pushed to ACR, tagged with the build ID.
4. Trivy scans the image.
5. The pipeline commits the new image tag to `terraform/app/deployment.yml`.
6. ArgoCD sees the commit and rolls the new version out.
7. The pipeline verifies the rollout and notifies Slack.

The pipeline never runs `kubectl apply`. Git is the source of truth for what is deployed, and ArgoCD reverts any manual drift in the cluster.

All of this is installed by Terraform, with chart versions pinned.

| --- | --- | --- | --- |

| ArgoCD | `argocd` | Syncs the application from this repository | 9.4.10 |

## Identity and secrets 🔐

No cloud credentials are stored in the cluster. Each workload has its own user-assigned managed identity, federated to its Kubernetes service account, with only the role it needs.

| Workload | Azure role | Why |
| --- | --- | --- |
| cert-manager | DNS Zone Contributor | Writes the TXT records for the DNS-01 challenge |
| external-dns | DNS Zone Contributor | Creates and updates A records |
| Grafana | Key Vault Secrets User | Reads its admin password |
| AttendanceCRM | Key Vault Secrets User | Reads the SQL connection string |
| AKS kubelet | AcrPull | Pulls images from the registry |

The SQL and Grafana passwords are generated by Terraform, stored in Key Vault, and mounted into pods by the Secrets Store CSI driver with rotation enabled. Nobody types or commits them.

## Observability

- **In the cluster:** Prometheus scrapes cluster and node metrics, Grafana serves dashboards over HTTPS, and both have persistent storage.
- **In Azure:** Container Insights sends node and pod data to Log Analytics, and Application Insights collects request and dependency telemetry from the app.
- **Alerting:** Azure Monitor rules cover high node CPU, high node memory and pod restarts, and email an action group.
- **From outside:** an availability test probes the public URL and checks how long the certificate has left.

## Repository layout

```
AttendanceCRM/                 .NET 6 MVC application, tests, Dockerfile, docker-compose
terraform/
├─ modules/                    acr, aks, alert_rule, appi, dns, kv, log,
│                              managed_identities, role_assignment, sql, vnet
├─ app/                        Manifests ArgoCD syncs (deployment, service, ingress, hpa)
├─ argocd/                     The ArgoCD Application
├─ k8s/                        Manifests Terraform renders with real values
│                              (ClusterIssuer, service accounts, SecretProviderClasses)
├─ helm-values/                Values for the platform charts
└─ main.tf, helm.tf, manifests.tf, namespaces.tf, provider.tf, variables.tf
azure-terraform-push.yml       Infrastructure pipeline
azure-terraform-destroy.yml    Destroy pipeline (manual trigger only)
azure-app-ci-cd.yml            Application pipeline
```

There are two manifest folders for a reason: `k8s/` holds files with placeholders that only Terraform can fill in (identity client IDs, the DNS zone name), while `app/` holds plain manifests that ArgoCD can apply as they are.

## Getting started 🚦

### Prerequisites
- A resource group and a public Azure DNS zone for your domain
- A storage account and container for Terraform state (see `terraform/backend.tf`)
- An Azure DevOps service connection
- A variable group 
- An Azure DevOps environment for approval check

### Build it
1. Run `azure-terraform-push.yml` and approve the Apply stage. This creates the infrastructure, the cluster and the platform.
2. Run `azure-app-ci-cd.yml`. This builds the image and commits its tag, and ArgoCD deploys it.
3. Wait a few minutes for DNS and certificates, then open the site.

### Tear it down
Run `azure-terraform-destroy.yml`. It never triggers automatically and needs the same approval.

### Run the app locally
Create `AttendanceCRM/.env`:

```bash
DB_SERVER=sql-server
DB_DATABASE=AttendanceCRM
DB_USER=sa
DB_PASSWORD=<a-strong-password>
```

Then:

```bash
cd AttendanceCRM
docker compose up --build
```

Browse to `http://localhost:5262/`. The app expects the AttendanceCRM database schema and an admin user to exist before you can sign in.

## Problems I hit and how I fixed them 🧠

| Symptom | Root cause | Fix |
| --- | --- | --- |
| Certificates stuck on "pending" with an authorisation error | A pipeline variable was missing, so the literal text `$(hosted_zone_name)` was rendered into the ClusterIssuer | Added the variable to the variable group and re-applied |
| Pods stuck in `ContainerCreating` after a rebuild | The SecretProviderClass had a hardcoded identity client ID, which went stale when the identity was recreated | Templated the value from Terraform |
| Site timing out after a rebuild | DNS still pointed at the old load balancer, and external-dns would not update records it did not own | Let external-dns recreate the records with its ownership markers |
| ArgoCD installed but no application deployed | The Application manifest was passed to the Helm chart as values, where it was ignored | Created it as its own Terraform resource |
| "Permission denied" on Terraform providers in the apply stage | Pipeline artifacts do not preserve file permissions | Published only the plan file and ran `init` again before apply |
| `kubectl` connecting to `localhost:8080` | Each pipeline stage runs on a fresh agent with no cluster credentials | Fetched credentials in every stage that needs them |

The common thread: most of these only appeared on a clean rebuild, which is why the destroy pipeline turned out to be the best test I had.
